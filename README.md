# memchat

A CLI chatbot demonstrating cross-session persistent memory using Jennah's public
memory APIs over HTTP/JSON via `jennah-proxy`.

By default, the chatbot delegates memory extraction and management to Jennah via
`memory:form`. The service extracts candidate memories from conversation turns,
reconciles them with existing workspace state, and commits the result atomically.
The chat model only generates the conversational reply.

The `-authored` flag switches to client-managed memory: the chat model uses a
`remember_fact` tool call, and the client converts the resulting triples into
graph nodes and edges committed via `memory:commit`.

This repository is a standalone Go module that interacts exclusively with the
public HTTP/JSON gateway authenticated by a `jennah_sk_` API key.

## Operating Modes

| Feature | Default (`memory:form`) | `-authored` (`memory:commit`) |
| --- | --- | --- |
| Memory extraction | Server-side (Jennah) | Client-side (`remember_fact` tool) |
| Extraction prompt | Managed by Jennah | Configured in client prompt/schema |
| Graph schema and IDs | Generated by Jennah | Derived client-side |
| Contradictions | Supersession history | Client-managed (last-write-wins) |
| Model tool calls | None | One per extracted fact |
| Metering/Cost | Formation requests | Chat model tokens |
| Turn latency | Seconds (formation pipeline) | Milliseconds (direct commit) |

## Architecture

Each turn executes a query-think-form cycle:

```
[User Input]
     │
     ├── 1. Query ───┬─ memory:query   (semantic search past turns)
     │               └─ memory:inspect (full graph retrieval)
     │
     ├── 2. Think ────  Generate reply (LLM)
     │
     └── 3. Form ────   memory:form (extract, recall, reconcile, commit)
```

1. **Query**:
   - `memory:query`: Performs semantic vector search across past turns. Query text
     is embedded by Jennah using server-managed embeddings.
   - `memory:inspect`: Retrieves known knowledge graph triples. Full inspection is
     used instead of traversal queries because edge endpoints (`source_node_id`,
     `target_node_id`) are needed to reconstruct direction regardless of phrasing.
2. **Think**: The LLM generates a response using the user message and recalled
   memory context. Under `-authored`, it is also provided the `remember_fact`
   tool schema.
3. **Form**: `memory:form` receives recent turns and returns a receipt containing
   extracted candidates and reconciliation decisions. Under `-authored`, the
   client commits graph elements directly via `memory:commit`.

### Turn Submission

Formation requests include a rolling window of the last 6 turns to provide
conversational context for resolving references across turns. Previously
extracted facts are deduplicated during reconciliation and marked as `known`.

Each formation request includes an idempotent key (`frm_<session>_<turn>`).
Retrying a request with the same key returns the existing receipt rather than
re-running extraction.

## Formation Receipts

With `-verbose` enabled, memchat prints candidate decisions returned by
`memory:form`:

```text
you> Actually I moved to Tokyo last week.

memo> Oh, congratulations on the move! ...
  [forming memory from 4 turn(s), key frm_sess_d310a0d4_2 ...]
  known    Hajime works as a backend engineer at Alphaus.
           (matches fct_b862ea8b...)
  revised  Hajime lives in Tokyo, having moved from Osaka.
           (retired fct_85ff9222...)
  known    Hajime works at Alphaus (matches rel_e52a9fc8...)
  revised  Hajime lives in Tokyo (retired rel_99f7081d...)
  formed:  log=1 vec=0(+1 superseded) nodes=2 edges=0(+1 superseded)
           @ 2026-09-22T03:34:12Z
  [memory] 2 earlier assertion(s) retired by a correction in this turn
           (superseded, not overwritten; kept in history)
```

- **Decisions**: Candidates are labeled `new`, `revised`, `known`, or `rejected`.
  Rejected candidates include a rejection reason (e.g. historical context cannot
  invalidate a current fact).
- **Supersessions**: Revised assertions update supersession counts rather than
  inserting new vector or edge records. Turns with only corrections show zero
  inserted records and non-zero supersessions.
- **Retention**: Retired assertions maintain their validity intervals and remain
  readable in history rather than being deleted.
- **Summary output**: Without `-verbose`, turns output a single line:
  `[formed: 2 new, 3 known]`.

Recalled chunks include provenance metadata displayed under `-verbose`:

```text
  ~ Hajime lives in Tokyo, having recently moved there from Osaka.
    [formed by frm_1f68a103..., turn(s) 0,2]
```

These reserved `jennah.*` metadata fields link formed memories back to originating
sessions and turns. Writes created under `-authored` do not include these fields.

## Schema Vocabulary

By default, formation extracts entities and relations using open-ended model
generation. Declaring a schema vocabulary restricts entity classes and relation
types in the extraction prompt to a predefined set. Off-vocabulary assertions are
not rejected; the vocabulary guides extraction generation.

`vocabulary.yaml` provides a sample vocabulary for personal assistant use cases
(6 classes, 9 relation types). To use a vocabulary, create and configure a
workspace with management credentials, then pass the workspace ID with `-agent`:

```sh
# 1. Create workspace and configure vocabulary (management credentials)
jnh agents create demo.memchat_vocab01 \
  --name memchat-vocab-demo --wait
jnh vocabulary declare \
  --scope demo.memchat_vocab01 \
  --from-file vocabulary.yaml
jnh vocabulary get --scope demo.memchat_vocab01

# 2. Run memchat targeting the configured workspace
./memchat -verbose -agent demo.memchat_vocab01
```

When `-agent` is provided, memchat connects to the specified workspace and does
not create or update `memchat-state.json`. If the workspace ID does not exist,
startup exits with an error.

To apply a vocabulary across all workspaces in an enterprise, omit `--scope`.
Scope-level declarations override enterprise defaults for that specific scope.

Vocabulary configuration requires `agent.vocabulary:manage` permissions. Reading
vocabulary configuration requires `agent.vocabulary:read`. If the API key lacks
read permissions, memchat logs a notice at startup and continues.

### Vocabulary Impact Example

Extraction results on two turns ("I am Kenji and I lead the platform team at
Nightblue." / "I live in Sapporo, and Nightblue is based in Tokyo. I am also into
bouldering."):

| Metric | Without vocabulary | With `vocabulary.yaml` |
| --- | --- | --- |
| Nodes | 5: Kenji, Nightblue, Sapporo, Tokyo, Bouldering | 6: adds `platform team` |
| Edges | 4: `WORKS_AT`, `LIVES_IN`, `LOCATED_IN`, `INTERESTED_IN` | 6: adds `LEADS` and `PART_OF` |
| Classes | None | Person, Organization, Team, Place, Interest |

Without a vocabulary, extraction collapsed the organizational structure into a
single relationship (`Kenji -WORKS_AT-> Nightblue`). Explicitly defining `Team`
as a class allowed extraction to recognize the team as an entity and preserve both
relationships (`Kenji -LEADS-> platform team` and
`platform team -PART_OF-> Nightblue`). Relation descriptions in the schema also
disambiguate usage, such as distinguishing `LIVES_IN` (individuals) from
`LOCATED_IN` (organizations).

## Memory Model and State

- **Session Continuity**: The agent workspace ID is persisted locally in
  `memchat-state.json`. Re-running the application resumes the existing agent
  memory. Deleting `memchat-state.json` creates a fresh agent workspace.
- **Workspace Namespacing**: Workspaces are created with the prefix
  `demo.memchat_<random>`. Role-based access policies targeting `demo.*`
  cover workspaces created by this tool.

Under `-authored`, the client is responsible for:

- **Graph Triples**: Mapping entity names to node labels and relationships to edge
  types.
- **Deterministic IDs**: Generating SHA-1 content hashes from labels to ensure
  consistent entity IDs across assertions.
- **Subject Resolution**: Managing subject references (mapping self-references to
  the dedicated `user` node ID).
- **Relationship Normalization**: Normalizing inverse relationship phrases before
  committing.

## Prerequisites

- **Jennah API Key**: A `jennah_sk_` key (`POST /v1/apikeys {"label":"memchat"}`
  or via console).
- **LLM Provider Credentials**: Either Anthropic Claude or Google Gemini:
  - **Anthropic**: `ANTHROPIC_API_KEY`
  - **Gemini (Google AI Studio)**: `GEMINI_API_KEY` or `GOOGLE_API_KEY`
  - **Gemini (Vertex AI)**: `GOOGLE_GENAI_USE_VERTEXAI=true`,
    `GOOGLE_CLOUD_PROJECT`, and Application Default Credentials

## Usage

### Quick Start

With Anthropic Claude:
```sh
export JENNAH_API_KEY=jennah_sk_...
export ANTHROPIC_API_KEY=sk-ant-...
go run .
```

With Google Gemini via AI Studio:
```sh
export JENNAH_API_KEY=jennah_sk_...
export GEMINI_API_KEY=...
go run .
```

With Google Gemini via Vertex AI:
```sh
gcloud auth application-default login
export JENNAH_API_KEY=jennah_sk_...
export GOOGLE_GENAI_USE_VERTEXAI=true
export GOOGLE_CLOUD_PROJECT=my-gcp-project
export GOOGLE_CLOUD_LOCATION=us-central1 # optional, defaults to global
go run .
```

### Example: Memory Correction and Supersession

To test contradiction handling and supersession:

```text
you> Hi, I am Hajime. I live in Osaka and work at Alphaus as an engineer.
you> Actually I moved to Tokyo last week.
```

Restart the session and query the stored state:

```text
you> Where do I live?
```

In default mode, the previous location is superseded in history rather than
overwritten. Under `-authored`, resolution depends on client-side logic.

### CLI Flags

| Flag | Env Var | Default | Description |
| --- | --- | --- | --- |
| `-endpoint` | `JENNAH_ENDPOINT` | `https://jennah.alphaus.cloud` | Jennah proxy origin URL |
| `-authored` | | `false` | Extract and commit memory client-side |
| `-provider` | | `auto` | LLM backend: `auto`, `gemini`, `anthropic` |
| `-region` | `JENNAH_REGION` | (default) | Region for agent creation (e.g. `us-central1`) |
| `-agent` | | | Use existing workspace ID without state file |
| `-state` | | `memchat-state.json` | Path to local state file storing agent ID |
| `-verbose` | | `false` | Print recalled snippets, facts, and receipts |

| `-anthropic-api-key` | `ANTHROPIC_API_KEY` | | Anthropic API key |

Exit a chat session with `/exit`, `/quit`, or Ctrl-D.

## Model Configuration

Default chat models:
- Anthropic: `claude-sonnet-5` (configured in `brain_anthropic.go`)
- Gemini: `gemini-3.8-flash` (configured in `brain_gemini.go`)

To configure other models (such as `claude-opus-4-8` or `gemini-2.5-pro`), update
the model constant in the corresponding provider file. Server-side formation
models are managed by Jennah per region and are not configured by the client.

## Implementation Notes

- **Timeouts**: Formation uses a dedicated HTTP client with a 300-second deadline.
  Because formation executes multiple inference and retrieval passes before
  committing, standard 60-second timeouts risk client cancellation while server
  processing completes.
- **Graph Recall**: Uses `memory:inspect` instead of traversal queries
  (`memory:query`). Traversal responses omit endpoint node IDs, whereas
  `memory:inspect` includes `source_node_id` and `target_node_id`.
- **Superseded Graph Assertions**: `memory:query` filters out superseded chunks.
  Graph inspection (`memory:inspect`) does not yet filter superseded edges by
  validity interval (`valid_at`/`invalid_at`), so superseded edges may remain
  visible in context until edge validity projection is supported.
- **Vocabulary Permissions**: Vocabulary status is logged at startup. Inspecting
  declared vocabulary requires `agent.vocabulary:read` on the API key.
- **Link Fusion**: Disabled (`link: false`) until backend support is available.

## Inspecting Stored Memory

To inspect the raw knowledge graph and memory stored in Jennah for an agent
workspace:

```sh
jnh scopes memory inspect <agent-id> --graph --all
```
